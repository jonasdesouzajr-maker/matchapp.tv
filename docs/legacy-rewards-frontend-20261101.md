# Independent Extra Matches rewards

This implements the owner's 1 November choice to add public rewards separately while preserving current allowances and payment behavior. It does not activate any server flag or claim live tablet/SSV verification.

`match-tokens.js` reuses its existing native reward state machine. The existing `match_token_status()` response continues to be the only owner of `enabled`, spending, promotion retirement, Pro and paid token presentation. When that master is off, a signed-in native Home or e-book page can read the separate authenticated `legacy_reward_status()` RPC. Its `legacy-rewards-v1` wallet must identify `extra_matches`, accurately add daily remaining and existing purchased matches, and report a supported existing 3/5/10/50 allowance. It never becomes the Match Tokens wallet.

Only a strict, enabled server wallet with successful owned history, exhausted included/Extra Match balances, and no ad-free/Pro entitlement offers the optional action. Home appends it to the preserved out-of-matches panel; e-books append it beside their existing controls. Browser, guest, Kids, other routes and nonexhausted accounts receive no independent offer. Native continues to own foreground/origin/document, first-value presentation, consent, ad-unit and SDK eligibility. Server-observed owned history is not provider-signed proof that a recommendation succeeded.

New first-value confirmation requests another status read after the existing Home history flush or successful e-book cloud write. It waits out an older status read, so an earlier response cannot swallow that observation. Existing save, matching, portfolio and quota functions keep their ownership.

The first trusted reward gesture creates or recovers a server-selected claim and prepares the existing native bridge. A matching `ready` event only exposes a second trusted Watch action. Prepared and terminal recovered claims reconcile without preparing/showing again. Claim destination is immutable; status responses that change it are rejected. Existing Match Token promises retain their destination and label, including after their rollout is paused. Disabled legacy wallets, including a subsequent ad-free/Pro purchase, remain usable to reconcile an already promised server reward.

SDK `earned`, `dismissed` and `serverVerified` fields never grant credits. Only authenticated claim status with `credited:true`, `status:credited`, the same nonce/destination and a valid server wallet displays success. The controller then refreshes the existing allowance badge and closes the old exhaustion panel; it never changes a local or server balance itself. The backend credits the original purchased-matches pool through genuine Google SSV. Ask AI, Stripe/Play products, prices, plans and debit paths remain unchanged.

Requests use the existing 12-second bound; native preparation has a 22-second cancellation bound. Server verification polls at most four more times, then offers manual refresh. Old request IDs, late loading/ready events, changed sessions, auth changes and hidden/unmounted documents cannot replay a show or install a prior account's wallet. Page restoration can reconcile a shown promise. No access token, nonce or account session is persisted by this flow.

The reward dialog temporarily makes the preserved exhaustion panel inert, restores its previous state on close/auth/pagehide, contains Tab/Shift+Tab and Escape, and retains focus when actions redraw. Its scoped CSS preserves font scaling and places it above the existing exhaustion overlay. No existing ad placement or geometry changes. Copy is authored for all fourteen supported languages; the old token reset terminology is excluded from the independent reward dialog.

Cache pins append `legacyrewards=20261101-1` only to the changed Match Tokens JS/CSS and e-book JS URLs. Ten existing HTML includes and the future finalizer path preserve their previous query parameters. No content or SEO generator was run.

Verification is in `tests/legacy-rewards-frontend.test.cjs`, the existing token/ebook/lifecycle tests, finalizer tests and the protected AdSense checks. `node tools/qa-legacy-rewards-20261101.cjs` runs local Chromium with current Home HTML/CSS, the shared notice-dialog owner and text-pill runtime, mocked account/native/status contracts, real trusted clicks, 130% font scale, keyboard focus checks, reduced motion and all fourteen languages at 320/390/820/1280 px. Output defaults to a fresh private temporary directory with the `matchapp-rewards-frontend-20261101-` prefix; an operator can set `MATCHAPP_REWARDS_QA_OUT` explicitly. These fixtures do not establish a live ad request, real SSV credit, physical-tablet result or publication. Public activation remains owned by the release operator after the required scoped verification.
